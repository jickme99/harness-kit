# Spec: graduation (hooks-by-evidence)

How the harness grows: by evidence from operation, never by design appetite. This page
governs every addition to the enforcement layer — and it is also the kit's self-updating
boundary.

## The invariants (MUST)

1. **The freeze rule:** no new harness components without evidence from running it. The
   bar for any addition is a documented miss or repeat friction from OPERATION.
2. **The graduation threshold: a class hand-fixed TWICE graduates to a mechanical guard.**
   One incident is an anecdote; two is a class. When the threshold is met, the fix is
   proposed as a hook, CI check, or guard — with the incident count tracked in the audit
   reports so the next audit can read it. The origin's guards are all graduates: the az
   guard (cross-tenant mistakes), the git scope guard (three ambient-state incidents in
   one hour — threshold met the same day), the merge-green guard (ten merges past a red
   main).
3. **Capture is automatic, proposal is automatic, ACTIVATION passes a gate.** Lessons are
   recorded as work progresses; graduation proposals are drafted by whoever hits the
   threshold; but **lessons touching strategy, gates, or the firewall are owner-level
   (T3) and never self-apply.** Self-learning with a human at the gate; anything else is
   unsupervised drift.
4. **A graduated guard arrives as a tested script** with both controls — the case it must
   block and the cases it must not (`spec/guards.md`) — and a live negative test proving
   the wiring fires. Fixed-twice earns a PROPOSAL, not a merge.
5. **Instruments that count graduations must themselves have readers.** The events ledger
   (fence hits, stop-and-asks, escalations — one JSONL line each) has a rollup reader run
   at close-out; seam names are the CLASS, not the instance, or the same failure recurring
   under three different strings produces three seams of one occurrence and no signal.

## The kit's own update loop (the same boundary, one level up)

Every stamped project carries `kit-manifest.json` — the checksummed fingerprint of
kit-owned files (`reference/tools/kit_manifest.py`). `classify` buckets each file
unmodified / customized / missing, which is what makes upgrades mechanical: unmodified
files may be regenerated by an upgrade PR; customized files are surfaced as conflicts,
never rewritten silently; missing files are never silently restored.

**Self-updating is PROPOSAL-ONLY: the kit opens PRs against consumer projects; projects
never self-apply.** Every upgrade goes through the consuming project's own Merge gate.
That machinery (the steward that reads consumer audit reports, harvests cross-project
lessons into kit PRs, and reads declined upgrades as kit feedback) is future work — it
activates at consumer #2 — but the manifest that enables it ships now, in every stamp.

File mechanics follow the upgrade-safe seam rule: kit-owned files are overwrite-clean;
project customization lives at designated seams (marked in the files themselves), so an
upgrade can never clobber a local adaptation.

## What an implementing agent must achieve

The threshold and the boundary are doctrine — constitution text plus the audit checklist
item that tracks hand-fix counts. The manifest is a stdlib Python script that runs
anywhere. What must survive: the twice-threshold, the activation gate on
strategy/gates/firewall, and proposal-only propagation.
